The 260 misses have three causes:

1. **Chained exceptions (208):** every `raise … from exc` and every exception raised while handling another. The parser read the last exception, the wrapper `RuntimeError("could not start the service")`, which isn't a version-change symptom.
2. **huggingface_hub's own wording (36 more; its 10 chained cases are counted above):** its lazy loader raises `AttributeError: No huggingface_hub attribute cached_download`, not Python's "module … has no attribute …". Missed in every presentation.

What held up on the first run: pytest's long and short output, unittest's, `logging.exception`'s, colour on 3.13 and 3.14, IPython's (its frames are in a format the parser doesn't read, but the message names the package or the installed versions supply it), and 3.14's new "Did you mean 'on_bad_lines'?" after an unexpected keyword argument.

## Fix: DT-CORE-25

- When the last exception isn't a shape DepTime analyses and a chain marker ("The above exception was the direct cause of the following exception:", "During handling of the above exception, another exception occurred:") joins it to the one before, the parser reads that one, and so on down the chain. Two errors in one log with no marker between them stay separate. `explain_error` says so in its note: "The last exception, RuntimeError, was raised from or while handling this ModuleNotFoundError, which is the one explained here."
- An `ExceptionGroup`'s bars are removed before parsing, so a sub-exception's line and frames read as in a plain traceback.
- `No <module> attribute <name>` on an `AttributeError` reads as a missing module attribute.

On the same 968 cases after the fix: 968 of 968. The fix was designed from these cases, so that's a regression check, not a measurement. `bench/cases` and `bench/tmb` don't change, case by case: only two of their 196 tracebacks are chained, and in both the last exception is the version change.
